## What to build (brief section 11, universal rules U30 and U48)
1. `src/server/ai/providers.ts`: a provider registry, OpenAI compatible chat completions for all of them:
   - gemini: https://generativelanguage.googleapis.com/v1beta/openai/chat/completions, key GEMINI_API_KEY, model gemini-3.5-flash-lite (family google_gemini).
   - openrouter: https://openrouter.ai/api/v1/chat/completions, key OPENROUTER_API_KEY, nvidia/nemotron-3-super-120b-a12b:free (nvidia_nemotron).
   - nvidia: https://integrate.api.nvidia.com/v1/chat/completions, key NVIDIA_API_KEY, nvidia/nemotron-3-super-120b-a12b (nvidia_nemotron).
   - requesty: https://router.requesty.ai/v1/chat/completions, key REQUESTY_API_KEY, nvidia/nemotron-3-ultra-550b-a55b (nvidia_nemotron) and google/gemma-4-31b-it (google_gemma). Timeout 12 s, at most 1 request in flight, at least 12 s between request starts.
   - cloudflare: https://api.cloudflare.com/client/v4/accounts/${CLOUDFLARE_ACCOUNT_ID}/ai/v1/chat/completions, key CLOUDFLARE_AI_TOKEN (needs CLOUDFLARE_ACCOUNT_ID too), @cf/openai/gpt-oss-120b (openai_gpt_oss).
   - zai: https://api.z.ai/api/paas/v4/chat/completions, key ZAI_API_KEY, glm-4.7-flash (zhipu_glm), timeout 45 s, 1 in flight.
   - kilo (keyless): https://ai-gateway.kilo.ai/api/v1/chat/completions, nvidia/nemotron-3-ultra-550b-a55b:free (nvidia_nemotron) and kilo-auto/free (family unknown).
   - ovh (keyless): https://oai.endpoints.kepler.ai.cloud.ovh.net/v1/chat/completions, gpt-oss-120b (openai_gpt_oss) and Qwen3.5-397B-A17B (alibaba_qwen). At least 30 s between calls to the same OVH model (2 a minute per model per IP). Meta-Llama-3_3-70B-Instruct is NOT in the agent rotation (it sent a boolean as the string "true"; docs note why).
   A provider whose key env is missing is skipped with reason no_key (gemini and nvidia today). Each provider has its own timeout (default 30 s), maxInFlight and minSpacingMs. Model lists can be overridden by env (for example AI_MODELS_REQUESTY as a comma list) but only for providers already in the registry.
2. `src/server/ai/chain.ts`: `createAiChain({ fetch, store, now, sleep, env, forcedDown })` and `chain.chat({ purpose, task, messages, tools, maxTokens, temperature, validate, agentFamily, conversationId, workspaceId, deadlineMs })`.
   - purpose 'agent' (the agent under test) order: requesty nemotron ultra, kilo nemotron ultra free, openrouter nemotron super free, ovh gpt-oss-120b, ovh Qwen3.5, zai glm-4.7-flash, cloudflare gpt-oss-120b, gemini, nvidia, then kilo-auto/free as the floor.
   - purpose 'judge' order: gemini, requesty gemma 4, ovh gpt-oss-120b, zai glm-4.7-flash, cloudflare gpt-oss-120b. A judge call MUST pass agentFamily and every model of that family is removed from the judge chain; kilo-auto/free (unknown family) is never a judge; if agentFamily is missing the judge call is refused with an error.
   - Per provider serialisation inside the process: a small per provider queue honouring maxInFlight and minSpacingMs (Requesty 1 in flight, 12 s spacing). Write a test with a fake clock.
   - Error handling per attempt, then move to the next model at once: HTTP 429 whose body mentions the day or quota being used up (per day, per-day, daily, neurons, free-models-per-day, quota) cools that model for 1 hour; any other 429 (rate or concurrency) cools that model for 60 s; 402 drops the whole provider for 24 hours; 401 and 403 drop the provider for 24 hours (bad key); 5xx, network error, timeout, empty reply, non JSON or malformed choices move on with no cooldown. A model or provider in cooldown is skipped with reason cooling.
   - Schema validation of tool calls: every tool call must name a tool in the given tools, its arguments must parse as JSON and match that tool's JSON schema strictly (types exact, a string "true" for a boolean is rejected, enum values, required fields, no extra properties when additionalProperties is false). Write a small checker for the JSON schema subset the manifest uses (object, properties, required, additionalProperties, string with minLength/maxLength/pattern/enum, boolean, integer, number, anyOf with null). A failing response is rejected with reason invalid_tool_args and the chain moves on. The caller may add `validate(response)` returning a reason or null.
   - A total deadline (deadlineMs, default 90 s) for one chat across all attempts.
   - Every attempt is recorded and tagged: { provider, model, family, outcome ok|error|skipped, reason (ok, no_key, cooling, dropped, forced_down, cap_reached, rate_limited, day_used, payment_required, auth_failed, timeout, http_5xx, network, invalid_response, invalid_tool_args, deadline), httpStatus, latencyMs }. The result is { content, tool_calls, meta: { provider, model, family, attempts, failover (true when the answer did not come from the first model tried), failoverReason (reason of the first failed attempt) } }. When no model answers, throw `AiChainExhausted` carrying the attempts (no provider text, no keys). Provider error bodies are cut to 200 characters and redacted of every env value that looks like a key before they go anywhere.
   - Fault injection: `forcedDown` (a set of provider ids or provider/model ids) makes those attempts fail with reason forced_down without any network call. Used by the probe.
3. Daily caps stored in the database (U48): test runs have their own cap so they never starve the live demo. Tasks: 'test_run', 'live_demo', 'probe'. Caps from env with defaults: AI_DAILY_CAP_TEST_RUN 300, AI_DAILY_CAP_LIVE_DEMO 400, AI_DAILY_CAP_PROBE 40; per provider daily caps (UTC day): openrouter 20 (its 50 a day is shared with the team), requesty 150, kilo 400, ovh 400, zai 200, cloudflare 100, gemini 200, nvidia 500 (env AI_PROVIDER_CAP_<ID> overrides). Every attempt that would reach the network first reserves one call; a refused reservation is reason cap_reached and the chain moves on. Failed calls count too.
4. Migration 0007_ai_chain.sql (schema nazir): tables ai_usage (UTC day, task, provider, model, calls, ok, failed; primary key day, task, provider, model), ai_cooldowns (provider, model or '*' for the whole provider, until, reason) and ai_calls (id, at, task, purpose, provider, model, family, outcome, reason, http_status, latency_ms, failover, attempt_no, workspace_id nullable, conversation_id nullable; NO prompt text, NO keys). RLS enabled and forced on all three, no direct table grants to any role. Narrow SECURITY DEFINER functions with SET search_path, EXECUTE revoked from PUBLIC and granted to nazir_worker only: `nazir.ai_reserve(task, provider, model, task_cap, provider_cap)` returns boolean (atomic under an advisory lock, counts the UTC day), `nazir.ai_record(...)` (writes ai_calls and updates ok or failed in ai_usage), `nazir.ai_cool(provider, model, until, reason)`, `nazir.ai_active_cooldowns()` and `nazir.ai_usage_today()` (read). Validate inputs inside the functions (short safe identifiers, caps >= 0).
5. `src/server/ai/store.ts`: interface AiStateStore with `memoryAiStore()` (tests, probe) and `postgresAiStore(driver)` that runs each call in a transaction with SET LOCAL ROLE nazir_worker and calls only the functions above. Cooldowns are read once per chat and kept in memory for the process as well.
6. `src/server/ai/chat-model.ts`: `chainChatModel(chain, { task, conversationId, workspaceId, onCall })` returns a `ChatModel` (the type in src/sandbox/agent.ts) for purpose 'agent', with the tool call validation on, and reports each answered call's meta through onCall so the runner can tag failover. Do NOT change src/sandbox/model-factory.ts or the sandbox route in this phase.
7. `scripts/ai-chain-probe.mjs` (load TS the way scripts/sandbox-agent-smoke.mjs does): env MAX_CALLS (default 6, hard maximum 20, counts every network attempt), PROBE_FORCE_DOWN (comma list), PROBE_PURPOSE agent|judge, PROBE_AGENT_FAMILY for judge. It sends one small fixed synthetic tool request (the create_case Arabic example from scripts/provider-preflight.mjs, fictional names only) through the chain with the memory store, prints one line per attempt (provider, model, outcome, reason, http status, latency) and the final answering provider and failover flag, never keys, never full responses. A `--scenarios` flag runs the sequence: nothing forced down, then the first answering provider forced down, then the first two, each sequentially, stopping when MAX_CALLS is used. Exit 1 if the chain was exhausted in the first scenario. Do NOT run it with the network; a parse test is enough.
8. docs/ai-chain.md: the registry, both chains and the family rule, limits and spacing, error classes and cooldowns, caps and how to change them, fault injection and the probe, what is recorded.

## What to build (brief section 10 Runner, ledger N10)
1. Migration 0008_runner.sql:
   - Status sets for nazir.runs and nazir.conversations become planned, queued, running, passed, failed, inconclusive, cancelled (replace the CHECK constraints in this new migration).
   - A state machine trigger on both tables: planned to queued or cancelled; queued to running or cancelled; running to queued (retry only), passed, failed, inconclusive or cancelled; passed, failed, inconclusive and cancelled are final (no change of status, and no change of the result columns after that). inconclusive requires a non empty inconclusive_reason. Applies to every role.
   - nazir.runs gains idempotency_key (unique per workspace when set) and calls_budget (int, copied from the plan). nazir.conversations gains available_at (default now()), max_attempts (default 3, 1 to 5), last_error (short code only), heartbeat_at, agent_version_id, scenario_hash, and a column for the final result summary (jsonb, set once).
   - `nazir.runner_claim(p_worker text, p_lease_seconds int)` SECURITY DEFINER, SET search_path, EXECUTE only for nazir_worker: picks the oldest conversation that is queued with available_at <= now(), or running with an expired lease, using FOR UPDATE SKIP LOCKED; an expired one with attempts used up becomes inconclusive with reason lease_expired and the search continues; otherwise sets status running, increments attempt on a reclaim, sets lease_owner, lease_expires_at, heartbeat_at and a fresh sandbox_tenant for this attempt (a short safe identifier from the conversation id and the attempt number, never reused), and returns workspace_id, conversation id, run id and attempt. When it claims the first conversation of a queued run, that run becomes running. Validate p_worker as a short safe identifier and the lease between 10 and 900 seconds.
   - `nazir.runner_heartbeat(p_conversation uuid, p_worker text, p_attempt int, p_lease_seconds int)` returns boolean: extends the lease only while lease_owner and attempt still match and the status is running.
   - The worker keeps its existing table grants; add only what the new columns or functions need. nazir_app, nazir_sandbox and nazir_inspector get nothing new.
2. `src/server/runner/` (server only modules):
   - `demo-scenarios.ts`: the two demo complaint scenarios as data, English (requester saeed, SR-1042) and Arabic (requester imran, SR-2077), each with resident_turns (use the three turns from scripts/sandbox-agent-smoke.mjs), requester_key, expected_state { category complaint, queue complaint_review, escalation_queue complaint_review, prior_request_ref, cases 1 } and a content hash. Fictional male names only.
   - `enqueue.ts`: `enqueueRun(driver, { workspaceId, planId, agentVersionId, scenarioIds, repeats, idempotencyKey })` as nazir_worker: the plan must be approved and in the workspace; the agent version's config must name a registry id (config.registry_id) that exists in getAgentVersion and its config_hash must equal that version's configHash (else refuse, the version drifted); scenarios must be approved and in the workspace; it writes the run (status queued, frozen_manifest with registry id, configHash, systemPromptHash, toolManifestHash, rulePackHash, scenario hashes, runner version and the AI chain order; manifest_hash = sha256 of the canonical manifest) and one conversation per scenario x repeat (status queued, idempotency_key = stable_key:language:repeat). Calling it again with the same idempotencyKey returns the same run and creates nothing new. Writes audit events run_enqueued.
   - `worker.ts`: `runNextConversation({ driver, inspectionDriver, chatModelFactory, evaluate, workerId, leaseSeconds, conversationTimeoutMs, now })` claims one item through nazir.runner_claim and processes it:
     a. seed the attempt tenant with sandbox.seed_tenant and check it is empty (no cases, no receipts) before the conversation starts; if not empty, mark the attempt inconclusive with reason dirty_tenant (never run on a used tenant);
     b. play the scenario's resident turns through runServiceAgent with the registry version, conversationKey = conversation id, the requester from the scenario, and a ChatModel from chatModelFactory (in production the N09 chainChatModel with task test_run and the postgres AI store; record every answered call's provider, model and failover; count calls into runs.calls_used and stop with inconclusive budget_reached when the run's calls_budget is used);
     c. a heartbeat every leaseSeconds/3 through nazir.runner_heartbeat; if the heartbeat fails the worker stops and writes nothing more (the lease was lost);
     d. a total conversation deadline (conversationTimeoutMs, default 180 s): when reached the attempt ends inconclusive with reason timeout;
     e. after the turns: write conversation_messages (resident and agent, in order), tool_events (one per tool call with request, response, outcome, idempotency key, payload hash), then read the inspection snapshot of the attempt tenant through the inspection channel and store it in state_readings (source inspection_channel, reading, reading_hash);
     f. the verdict comes from `evaluate({ scenario, version, reply, transcript, toolCalls, reading })`, which returns { status: 'passed' | 'failed' | 'inconclusive', reason?, results }. N10 ships a default evaluator that returns inconclusive with reason checks_missing (N11 replaces it). Rules that override the evaluator: if any model call ended with AiChainExhausted (detect it in the ChatModel wrapper, because runServiceAgent turns model errors into its fallback reply), the timeout fired, the budget ran out or the reading is missing, the result is inconclusive with that reason, never passed; any value other than the three statuses is inconclusive with reason bad_evaluator;
     g. retries: only inconclusive with an infrastructure reason (provider_exhausted, timeout, lease_expired, dirty_tenant, reading_failed) is retried, with backoff (available_at = now + 30 s times attempt), while attempt < max_attempts; the item goes back to queued and the next claim gets a fresh tenant. passed and failed are final and NEVER retried (a failure must not be rerun until it passes);
     h. every final or retry write is conditional on lease_owner, attempt and status running still matching (a worker that lost its lease cannot overwrite the new attempt);
     i. when every conversation of the run is final, the run status is: cancelled if it was cancelled, failed if any conversation failed, inconclusive if any is inconclusive (reason names how many), passed only if every conversation passed; finished_at set;
     j. audit events through nazir.append_audit: conversation_claimed, conversation_retried, conversation_finished (status, reason, provider, model, failover), lease_recovered, run_started, run_finished, run_cancelled. Payloads carry ids, codes and hashes only, no transcript text.
   - `cancel.ts`: `cancelRun(driver, workspaceId, runId)` sets the run and every non final conversation to cancelled; a worker that finishes after a cancel writes nothing over it (its conditional update fails) and a cancelled conversation never becomes passed.
3. `scripts/runner-fixture.mjs` (takes DATABASE_URL_OWNER): idempotently creates a synthetic fixture workspace "Nazir runner fixture" (via nazir.bootstrap_workspace as nazir_worker, fixture member with a fictional name), the demo agent with three agent_versions for baseline, planted_wrong_queue and planted_false_submit (config { registry_id }, config_hash from the registry, kind and fault_label from the registry disclosure), the demo rule pack version (approved), a built_in adapter, the scenario meaning and the two scenarios (approved) and an approved plan (budget_calls 60). Prints only ids and PASS lines, never addresses. One transaction, committed only at the end.
   `scripts/runner-run.mjs` (takes DATABASE_URL = app login, INSPECT_DATABASE_URL = inspection login, AI keys from env): VERSION (registry id), LANGUAGES (en,ar), IDEMPOTENCY_KEY, MAX_CONVERSATIONS (default 2, max 6), MAX_CALLS (hard cap on network AI calls for the whole process, default 24, max 60); enqueues a run on the fixture workspace, then works the queue until that run is final or a cap is hit, and prints per conversation: status, reason, provider, model, failover, tenant, case references and queues from the reading, and the run status. Never prints keys, addresses or full transcripts. Do NOT run either script (no network); a parse test is enough.
4. docs/runner.md: states and transitions, the queue and leases, claim and recovery, tenant per attempt (the reset is a fresh tenant, old attempts stay as evidence), idempotency at enqueue, conversation and tool level, retries and what is never retried, timeouts and budget, how inconclusive can never become passed, audit events, the scripts.
